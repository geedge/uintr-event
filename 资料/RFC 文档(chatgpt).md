# 用户中断介绍

用户中断（Uintr）是一种硬件技术，它可以直接将中断传递到用户空间。

今天，几乎所有特权边界上的通信都要通过内核进行。这些包括信号、管道、远程过程调用和基于硬件中断的通知。用户中断通过避免通过内核的转换，为这些常见操作提供了更高效的（低延迟和低CPU利用率）版本。

在用户中断的硬件架构中，接收方始终预期是一个用户空间任务。然而，用户中断可以由另一个用户空间任务、内核或外部源（如设备）发送。

除了接收用户中断的一般基础设施外，本系列介绍了一个单一来源：来自另一个用户任务的中断。这些被称为用户 IPI。

用户 IPI 的第一个实现将出现在代号为 Sapphire Rapids 的英特尔处理器中。有关硬件架构的详细信息，请参阅英特尔架构指令集扩展的第11章 [1]。

# 它是如何在底层工作的？-硬件摘要

用户中断是一种已发布的中断传递机制。中断首先发布到内存位置，然后在运行时CPL=3时直接传递到接收器。

## 内核管理的体系结构数据结构

UPID: 用户发布的中断描述符-保存接收器中断向量信息和通知状态（如正在进行的通知，被抑制的通知）。

UITT: 用户中断目标表-存储 UPID 指针和向量信息，用于发送方的中断路由。由 senduipi 指令引用。

每个任务的中断状态通过 MSRs 引用，这些 MSRs 在上下文切换期间由内核保存和恢复。

## 指令

`senduipi <index>` - 向目标任务发送一个用户 IPI，基于 UITT 索引。

clui - 通过清除 UIF（用户中断标志）来屏蔽用户中断。

stui - 通过设置 UIF 来取消屏蔽用户中断。

testui - 测试 UIF 的当前值。

uiret - 从用户中断处理程序返回。

## 用户 IPI

当用户 IPI 发送方执行  `"senduipi<index>"` 时，硬件会引用由索引指定的 UITT 表条目，并将中断向量（63-0）发布到接收器的 UPID 中。

如果接收器正在运行（CPL=3），发送方 CPU 将向接收器 CPU 发送一个物理 IPI。在接收方侧，这个 IPI 被检测为用户中断。接收器的用户中断处理程序被调用，并将向量号（63-0）推送到堆栈中。

在中断处理程序执行 "uiret" 后，控制被转移到被中断的指令处。

有关详细信息，请参阅英特尔架构指令集扩展的第11章 [1]。

## 应用程序接口 - 软件架构

用户中断 (Uintr) 是一项选择性功能（与信号不同）。希望使用 Uintr 的应用程序应使用与 Uintr 相关的系统调用向内核注册自己。Uintr 接收器始终是一个用户空间任务。Uintr 发送方可以是另一个用户空间任务、内核或设备。

1. 接收方可以使用 Uintr 接收方相关的系统调用注册/注销中断处理程序。\
   uintr_register_handler(handler, flags)\
   uintr_unregister_handler(flags)

2. 系统调用还允许接收方注册向量并创建用户中断文件描述符 - uintr_fd。\
   uintr_fd = uintr_create_fd(vector, flags)

在某些使用频繁的用户空间事件通知的用途中，Uintr 可能很有用，例如 eventfd 或信号。uintr_fd 的语义与 eventfd() 或管道的写端类似。

3. 具有对 uintr_fd 访问权限的任何发送方都可以使用它向接收方传递事件（在本例中为中断）。发送方任务可以使用与 uintr_fd 相关的系统调用来管理与接收方的连接。\
   uipi_index = uintr_register_sender(uintr_fd, flags)

使用 FD 抽象提供了一种安全的机制来连接接收方。内核实现的 FD 共享和隔离机制也将扩展到 Uintr。

4a) 在初始设置之后，发送方任务可以使用 SENDUIPI 指令和 uipi_index 生成用户 IPI，而无需任何内核干预。\
SENDUIPI <uipi_index>

如果接收方正在运行（CPL=3），则直接传递用户中断，无需内核转换。如果接收方未运行，则在接收方重新上下文切换时传递中断。如果接收方被阻塞在内核中，则将用户中断传递给内核，然后解除预期的接收方以传递中断。

4b) 如果发送方是内核或设备，则可以将 uintr_fd 传递到相关的内核实体以允许它们建立连接，然后生成用户中断以进行事件传递。 <该 API 的确切细节仍在努力工作中。>

有关用户界面和相关系统调用的详细信息，请参见 Uintr 手册草案：\
[https://github.com/intel/uintr-linux-kernel/tree/rfc-v1/tools/uintr/manpages。](https://github.com/intel/uintr-linux-kernel/tree/rfc-v1/tools/uintr/manpages%E3%80%82)\
我们还将相同的内容包含在这个系列的补丁 1 中，以便更容易地进行审查。

# 内核设计选择

以下是当前 API 设计的一些原因和权衡。

## 系统调用接口

为什么使用系统调用接口？：我们考虑的两种选项是在 /dev 中使用字符设备或使用系统调用（当前方法）。系统调用方法避免了通过驱动程序模型公开核心 CPU 功能的问题。此外，我们希望每个向量都有一个用户中断 FD，并在所有向量之间共享一个公共中断处理程序。这似乎更容易通过基于系统调用的方法来实现。

使用用户中断共享/传输数据：Uintr 不包括共享/传输数据的机制。期望应用程序使用现有的数据共享机制来共享数据，仅使用 Uintr 进行信号传递。

为每个向量分配一个 FD：为每个向量分配一个 uintr_fd，以允许接收方进行精细的优先级和事件管理。我们考虑的另一种选择是将 FD 分配给中断处理程序，并将其与发送方共享。但是，这种方法依赖于发送方选择向量，并将向量优先级管理移动到发送方。此外，如果多个发送方想要发送独特的用户中断，它们需要在它们之间协调向量选择。

扩展 API：目前，系统调用仅可使用标志参数进行扩展。如果需要，我们可以向某些系统调用添加可变大小的结构。

## 扩展现有机制

在某些使用 eventfd() 或信号的用途中，Uintr 可能很有用。由于 Uintr 是硬件相关的、线程特定的，并且在快速路径中绕过内核，因此它使扩展现有机制变得更加困难。

扩展信号的主要问题：  
信号处理程序与用户中断处理程序的定义方式有很大的不同。应用程序需要在用户中断处理程序中保存/恢复寄存器并调用 uiret 进行返回。此外，信号可以是进程导向的（或线程导向的），但用户中断始终是线程导向的。

将信号与用户中断进行比较：  
+=====================+===========================+===========================+  
| | 信号 | 用户中断 |  
+=====================+===========================+===========================+  
| 堆栈 | 具有备选堆栈 | 使用应用程序堆栈 |  
| | | （尚未启用备选堆栈选项） |  
+---------------------+---------------------------+---------------------------+  
| 寄存器状态 | 内核管理，包括 FPU/XSTATE 区域 | 应用程序负责（使用 GCC |  
| | | 的 'interrupt' 属性用于通 |  
| | | 用通用寄存器） |  
+---------------------+---------------------------+---------------------------+  
| 阻塞/屏蔽 | sigprocmask(2)/sa_mask | CLUI 指令（没有每个向量屏蔽） |  
+---------------------+---------------------------+---------------------------+  
| 方向 | 单向 | 单向 |  
+---------------------+---------------------------+---------------------------+  
| 后续事件 | kill()，signal()，sigqueue() 等 | SENDUIPI <index> - 索引从 uintr_fd |  
| | | 派生 |  
+---------------------+---------------------------+---------------------------+  
| 目标 | 进程导向或线程导向 | 线程导向 |  
+---------------------+---------------------------+---------------------------+  
| Fork/继承 | 空信号集 | 什么也不继承 |  
+---------------------+---------------------------+---------------------------+  
| Execv | 保留待处理信号 | 什么也不继承 |

+---------------------+---------------------------+---------------------------+  
| 处理程序重新进入 | 除正在处理的信号外，所有信号 | 没有中断可以导致处理程序重新进入。|  
| | | |  
+---------------------+---------------------------+---------------------------+  
| 传递反馈 | 基于信号是否已发送为 0 或 -1 | 没有反馈，无法确定是否已发送或 |  
| | | 接收到中断。 |  
+---------------------+---------------------------+---------------------------+

扩展 eventfd() 的主要问题：  
eventfd() 具有对 API 核心的计数器值。用户中断无法具有相关联的计数器，因为信令发生在用户级别，而硬件没有内存计数器机制。此外，eventfd 可用于双向信令，而 uintr_fd 是单向的。

将 eventfd 与 uintr_fd 进行比较：  
+====================+======================+==============================+  
| | eventfd | uintr_fd（用户中断 FD） |  
+====================+======================+==============================+  
| 对象 | 计数器-uint64 | 接收方向量信息 |  
+--------------------+----------------------+------------------------------+  
| 发送事件 | 写入 eventfd | SENDUIPI <index> - 索引从 uintr_fd |  
| | | 派生 |  
+--------------------+----------------------+------------------------------+  
| 接收事件 | 读取 eventfd | 隐式-处理程序与关联的向量一起调用 |  
| | | |  
+--------------------+----------------------+------------------------------+  
| 方向 | 双向 | 单向 |  
+--------------------+----------------------+------------------------------+  
| 传输的数据 | 计数器-uint64 | 没有 |  
+--------------------+----------------------+------------------------------+  
| 等待事件 | Poll() 系列系统调用 | 没有每个向量等待。 |  
| | | uintr_wait() 允许等待所有用户中断 |  
+--------------------+----------------------+------------------------------+


# 安全模型

用户中断是一种自愿选择的功能（不像信号）。用户中断的安全模型旨在类似于 eventfd()。一般的想法是，任何具有 uintr_fd 访问权限的发送方都可以为创建了该 fd 的接收任务生成关联的中断向量。

## 不受信任的进程

当前的实现预计只有可信且协同的进程使用用户中断进行通信。在协调连接拆除的情况下，期望进程之间进行协调。在协调不发生的情况下（比如由于进程突然退出），内核将继续保持共享资源（如 UPID）分配以避免故障。

目前，发送方可以通过生成一连串的用户中断轻易地导致接收方的拒绝服务。用户中断处理程序在禁用中断的情况下被调用，但在执行 uiret 后，硬件会再次启用中断。这可能会导致在正常执行恢复之前再次调用处理程序。没有硬件机制来屏蔽特定的中断向量。

为了使不受信任的进程能够进行通信，我们需要通过另一个系统调用（或者可能是 IOCTL）添加每个向量屏蔽选项。但是，这可能会增加内核代码的复杂性。只能通过修改源头的 UITT 条目来屏蔽向量。在删除和恢复 UITT 的 UPID 时，我们需要小心竞态条件。

## 资源限制

接收方-发送方连接的最大数量将受到打开文件描述符的最大数量和 UITT 大小的限制。

目前，UITT 大小是任意选择的 4kB 固定大小。我们计划将其更改为动态和可配置的大小。当达到大小限制时，应触发 RLIMIT_MEMLOCK 或 ENOMEM。

# 主要开放

## 中断阻塞

如果应用程序在用户空间运行，则用户中断会立即传递给应用程序。如果接收任务使用占位符 uintr_wait() 系统调用在内核中阻塞，任务将被唤醒以传递用户中断。但是，如果任务由于任何其他阻塞调用（如 read()、sleep() 等）而被阻塞，则只有在应用程序再次调度时才会传递中断。我们需要考虑如果应用程序需要在发布时立即接收用户中断（类似于信号），当它们由于某些其他原因而被阻塞时。添加此功能可能会使内核实现更加复杂。

使用用户中断中断系统调用也意味着我们需要考虑一种 SA_RESTART 类型的机制。我们还需要评估内核中是否可以重用一些与信号处理程序相关的语义来处理用户中断。

## 共享用户中断目标表（UITT）

当前实现为每个任务分配一个唯一的 UITT。这意味着用户中断用于两个任务之间的点对点通信。此外，这使得内核实现相对简单。

但是，共享 UITT 对于多线程应用程序的线程之间也有好处。其中一个好处是，它们将看到 UITT 的一致视图。即 SENDUIPI <index> 在应用程序的所有线程上都具有相同的含义。此外，每个线程都不必使用常用的 uintr_fd 注册自己。这将简化用户空间设置并有效利用内核内存。潜在的缺点是内核实现分配、修改、扩展和释放 UITT 将更加复杂。

对于一组彼此之间进行大量 IPC 的进程，也可以提出类似的论点。他们会更喜欢有一个共享的 UITT，让他们可以从任何进程针对任何进程。使用当前基于文件描述符的方法，连接设置可能会耗费时间并有些繁琐。我们需要评估是否可以使其更简单。

## 内核页面表隔离（KPTI）

SENDUIPI 是一个特殊的 ring-3 指令，它对 UPID 和 UITT 内存进行了监管模式内存访问。当前的补丁需要禁用 KPTI 才能使用户 IPI 正常工作。要使用户 IPI 与 KPTI 正常工作，我们需要从具有监管访问但被映射到用户空间的特殊内存区域分配这些结构。计划实现类似于 LDT 的机制。

支持用户中断的处理器不受 Meltdown 影响，因此 KPTI 的自动模式将默认关闭。想要强制启用 KPTI 的用户需要等待这个补丁系列的后续版本才能使用用户中断。请告诉我们是否希望优先处理（或降低处理）这些补丁的开发。

# 常见问题解答

问：如果一个进程“意外”收到了用户中断会发生什么？  
答：对于没有向内核注册并请求用户中断的任务，不应该或无法接收到用户中断。

问：用户中断是否会影响内核调度？  
答：不会。如果一个任务被阻塞等待用户中断，当内核代表该任务接收到通知时，我们只会将其放回运行队列。用户中断的传递不会以任何方式改变任务的调度优先级。

问：发送方是否会知道中断是否已经被传递？  
答：不会。用户中断只提供了一种已发布的中断传递机制。如果应用程序需要依赖于中断是否已经传递，它们应该考虑使用用户空间机制进行反馈（如共享内存计数器或向发送方发送用户中断）。

问：为什么没有关于中断传递的反馈？  
答：由于是发布的中断传递机制，中断传递发生在两个步骤中：  
1）中断信息存储在内存位置（UPID）中。  
2）物理中断传递给中断接收方。

第二步可能会立即发生，在延迟的一段时间后发生，或者可能永远不会发生，这取决于第一步后接收方的状态。（接收方可能已经禁用中断，在此期间被上下文切换出去，或者可能在此期间崩溃。）这使得硬件很难在执行SENDUIPI时可靠地提供反馈。

问：用户中断可以嵌套吗？  
答：可以。在中断处理程序中使用STUI指令将允许传递新的用户中断。但是，没有类似TPR（线程优先级寄存器）的机制，允许只能处理更高优先级的中断。当启用嵌套时，任何用户中断都可以被接受。

问：一个任务是否可以一次性接收所有待处理的用户中断？  
答：不行。硬件只允许一次处理一个向量。如果一个任务对待处理的所有中断感兴趣，那么我们可以添加一个系统调用来提供待处理中断的信息。

问：进程需要绑定到CPU上吗？  
答：不需要。用户中断将正确路由到接收方运行的任何CPU上。在上下文切换期间，内核会更新UPID中的CPU信息。

问：为什么UPID和UITT由内核分配？  
答：如果由用户空间分配，应用程序可能会滥用UPID和UITT来写入未授权的内存，并在任何CPU上生成中断。UPID和UITT由内核分配，并通过特权级访问硬件。
